> Disusun 2026-08-12 dari audit 80-agent + riset paper/dokumentasi/implementasi referensi (Aptos, Sui, Narwhal/Bullshark, Block-STM, Tendermint BFT-time) + pembacaan source move-vm asli di mesin ini.

## Ringkasan

Verified against source: all four blockers are real as described. `execute_transaction_actions` (core/vm_move/src/lib.rs:462-556) unconditionally calls `session.finish()` after an abort and returns the partial changeset; `absorb_vm_result` (core/executor/src/lib.rs:2739-2757) pushes those writes into `updates` before reading `status.success`, and the batch commit loop (:1595-1633) writes them into a RocksDB WriteBatch and folds them into `sys:state_root`. `analyze_tx` (:2174+) hand-writes per-module dep sets while `schedule_batches` (:2357-2394) batches on those sets and the commit loop is last-write-wins per key (:1599-1612). `dag.rs:816-820` sets `current_round = vertex.round + 1` from one remote vertex while `try_create_vertex` (:331-379) takes parents only from `current_round - 1` behind a stake-weighted quorum gate. `ordering.rs:493-510` picks the anchor by round-robin over whichever leader vertex happens to be local, and `find_causal_history` (:752-770) silently skips parents missing from the local DAG. Confirmed extras: `blockchain/src/lib.rs:56` bakes `SystemTime::now()` into the header hash at the sole call site `dag.rs:911`, and `sync/src/lib.rs:974` calls `execute_block_parallel`, which commits to RocksDB internally (:1633), BEFORE `verify_execution_roots` at :976.

The plan is 12 steps in dependency order. Atomicity ships first because it is the root of the DEX brick, the fund-destruction PoC and the credit-before-debit mints, and because the staged prologue adds write keys (the gas payer's CoinStore) that the B2 conflict-token fix must already know about. Header determinism ships before the consensus work because you cannot verify B3/B4 fixes — or fix the sync verify-before-commit hole — while every node derives a different block hash for identical content. B3 (liveness) before B4 (safety) because a wedged chain cannot produce the payload-carrying blocks that B4's determinism gate needs to be tested against.

One fresh genesis is required, once, immediately before burn-in (Step 11). It is essentially free: the audit found only 2 of 349k rounds carried transactions, and mainnet has not launched. A second genesis is only needed if a state-transition change lands after burn-in begins.

The single largest risk is not any individual blocker: it is that the payload execution path has effectively never run. `bench-tps/src/main.rs:62` still emits the legacy string payload `"transfer:{to}:1:{nonce}"`, which the BCS-only mempool rejects — so there is currently no tool on this machine capable of putting real load on the code these fixes touch. Building that tool is Step 2 and it gates every "done when" that follows.

### Langkah 5 — B2b — runtime read/write footprint tracing + batch validation & re-execution (durable layer)
**File:** `/Users/macbookpro/Documents/AINCORE-Blockchain/core/vm_move/src/lib.rs (TracingStorage), /Users/macbookpro/Documents/AINCORE-Blockchain/core/executor/src/lib.rs (execute_block_parallel 1518-1640)`
**Kenapa urutan ini:** Step 4 is correct only as long as the hand-written table stays in sync with the Move source; the next stdlib change silently invalidates it. This step demotes analyze_tx from a safety boundary to a pure performance hint, which is what Block-STM does (Gelashvili et al., 'Block-STM: Scaling Blockchain Execution by Turning Ordering Curse to a Performance Blessing'): execute optimistically, VALIDATE against what earlier transactions actually wrote, re-execute on conflict. **Selesai kalau:** (a) A commit-time safety net in the batch loop detects two distinct tx_hashes staging the same key within one batch and, instead of silently last-write-wins, discards and deterministically re-runs — with a metric counter exported. ### Langkah 6 — Block header determinism — remove SystemTime::now() from the header hash
**File:** `/Users/macbookpro/Documents/AINCORE-Blockchain/consensus/blockchain/src/lib.rs:45-70, /Users/macbookpro/Documents/AINCORE-Blockchain/consensus/consensus/src/dag.rs:900-925`
**Kenapa urutan ini:** Blocking prerequisite for Steps 7, 9, 11 and 12. new_with_roots calls SystemTime::now() inside the constructor and folds the result into the header hash; the sole call site is dag.rs:911, so today two honest nodes committing byte-identical content derive different block hashes. ### Langkah 8 — B3 — derive current_round from parent-quorum availability, never from a single remote vertex
**File:** `/Users/macbookpro/Documents/AINCORE-Blockchain/consensus/consensus/src/dag.rs:805-822 and 331-385`
**Kenapa urutan ini:** Liveness before safety: a wedged chain cannot produce the payload-carrying blocks that Step 9's determinism gate must be tested against. The bug is confirmed — dag.rs:816-820 sets current_round = vertex.round + 1 from one remote vertex and persists it as latest_proposed_round, while try_create_vertex (:331-338) draws parents only from current_round - 1 and gates on stake-weighted parent quorum (:346-379). One vertex a single round ahead moves the node to a round whose predecessor can never reach quorum, and try_create_vertex stops forever, persisted across restarts. MAX_ROUND_JUMP=10000 (:632) is irrelevant because a jump of 1 does it. No Byzantine intent needed: a validator with a fast ticker suffices. The correct rule is Narwhal's (Danezis, Kokoris-Kogias, Sonnino, Spiegelman, EuroSys 2022) and DAG-Rider's: a validator advances to round r+1 only upon collecting 2f+1 certificates for round r — availability of quorum drives the round, never a peer's claim. Recompute current_round on ingest as (highest round whose round_index holds stake quorum) + 1, monotonic non-decreasing; genuine amnesia recovery then flows through the sync path, not through a round jump.
**Selesai kalau:** test_b3_fast_ticker_peer_cannot_wedge: a 4-node harness where node D's ticker runs 5x fast; after 500 rounds all four nodes are still producing vertices and the committed height gap between fastest and slowest is bounded (<10). test_b3_round_never_exceeds_quorum_plus_one: property test over randomized vertex arrival orders asserting current_round <= (max round with stake quorum) + 1 always. test_b3_restart_recovers: kill a node mid-run, restart, confirm it rejoins and resumes proposing within 30 seconds without manual intervention (the persisted latest_proposed_round no longer strands it). Long-partition recovery still works: isolate a node for 200 rounds, reconnect, confirm it catches up via sync.

## Gate (wajib lolos)

1. GATE 1 (after Step 1) — no aborted transaction may commit a single user write. Proof: the original fund-destruction PoC yields sender = start - gas exactly, and test_b1_empty_prologue_abort_returns_empty_writeset passes. Nothing downstream ships until this holds.

2. GATE 2 (after Step 2) — a real BCS load generator exists and drives >=50 TPS with a controllable abort rate. Without it, every subsequent 'done when' is unfalsifiable; this is a hard gate, not a nice-to-have.

3. GATE 3 (after Steps 4+5) — parallel execution is byte-identical to serial execution across 100 randomized 500-tx mixes, INCLUDING with analyze_tx deliberately sabotaged. This is the proof that transaction scheduling is no longer a safety boundary.

4. GATE 4 (after Step 6) — two nodes committing identical content derive identical block hashes. Verified over 1000 blocks by tools/state-diff. Blocks Steps 7, 9, 11, 12.

5. GATE 5 (after Step 8) — no single peer vertex can stop local block production. A 4-node run with one 5x-fast ticker keeps all four proposing for 500 rounds, and a killed node rejoins unattended within 30s.

6. GATE 6 (after Step 9) — commit ordering is arrival-order independent. 1000 shuffled arrival permutations of one DAG produce identical committed sequences, and a missing parent defers rather than silently skipping.

7. GATE 7 (before Step 11) — systemd auto-start proven by hard-rebooting every validator machine, and validator count >=4 on >=4 distinct machines (f>=1). No burn-in clock starts before this.

8. GATE 8 (Step 11, the mainnet gate) — 72h+, >=4 validators, >=100k non-empty blocks, >=1M txs, >=20% aborting txs, ZERO state_root/block_hash divergence, zero halts, zero manual interventions, supply invariant holds every 1000 blocks, a fresh node syncs from genesis to the identical head state_root.

## Genesis baru?

YES — exactly once, at Step 11, immediately before burn-in begins.

Which steps force it: Step 1 changes the write set of every aborted transaction, hence sys:state_root and every receipt hash. Step 3 changes compiled stdlib module bytes. Steps 4 and 5 change which writes survive a batch. Step 6 changes the block header hash preimage. Any of these alone makes old and new binaries fork on the first affected block, so a rolling upgrade is not an option under any circumstances — the only two valid paths are a fresh genesis or a coordinated full stop, upgrade all machines, restart.

Cost of a fresh genesis here is essentially zero and this is the decisive fact: the audit established that in 349k rounds only 2 blocks carried transactions at all, and mainnet has not launched. There is no meaningful transaction history to preserve, so preferring a fresh genesis over a stop-and-restart is strictly safer at no cost — it also guarantees no residue of the pre-fix state transition (partially-committed aborted writes, a bricked DEX pool, a corrupted ValidatorSet blob) survives into the chain being burned in.

Sequencing detail: do NOT regenerate genesis after Step 1 and again after Step 6. Land Steps 1, 3, 4, 5, 6, 7, 8, 9 on the branch, ship them as one binary, then cut ONE genesis at Step 11. Every step's intermediate verification runs on local throwaway datadirs, which cost nothing to recreate.

A SECOND genesis is required only if any state-transition or header change lands after the Step 11 burn-in clock starts. If a fix is needed mid-burn-in, the correct response is: land it, cut a new genesis, restart the 72h clock from zero. Do not carry a burn-in result forward across a state-transition change.

Per CLAUDE.md rule 1, regenerating genesis.json needs explicit founder confirmation at that moment — it is not implied by approving this plan.

## Risiko terbesar

1. THE PAYLOAD PATH HAS NEVER RUN. 2 non-empty blocks in 349k rounds, and bench-tps/src/main.rs:62 still emits a legacy string payload the BCS-only mempool rejects — so nothing in the DEX, delegation, token_factory or staking entry paths has meaningful production hours. Expect Step 11 to surface NEW bugs unrelated to the four blockers. Mitigation: Step 2 is a hard gate, and the burn-in criteria demand >=20% deliberately-aborting transactions so failure paths get exercised at scale, not just happy paths. Budget for a burn-in restart.

2. STEP 9 IS THE SCHEDULE RISK. Deterministic anchoring plus a causal-completeness gate plus a brand-new vertex-fetch path is the only step that adds protocol surface rather than fixing existing code. The completeness gate can deadlock if the fetch path is unreliable (defer forever waiting on a parent nobody serves). Mitigation: build the fetch path FIRST and prove the round trip on live nodes before turning on the defer behaviour; add a bounded retry with a metric so a stalled fetch is loud rather than a silent halt; keep the fetch serving in chain_sync::handle_message per the repo's unified-serving convention rather than adding a second serving path.

3. FIXING B1 WITHOUT FIXING B2 CREATES A NEW CONFLICT. The staged prologue means EVERY transaction now provably writes resource_{payer}_CoinStore, a key that many analyze_tx branches do not declare. Shipping Step 1 alone would increase, not decrease, the odds of a scheduler-induced state-root fork. Mitigation: Steps 1 and 4 must reach mainnet together; they may land as separate commits but must never be separated by a genesis or a burn-in boundary.

4. THE 'IT LOOKS RIGHT' FAILURE MODE. This repo has shipped two fixes that were correct as functions but never executed on the live path. All four blockers survived 16 hardening commits. Mitigation: every "done when" above is stated as an executed observation (a PoC that now fails, a counter that is non-zero, a divergence tool reporting zero over N blocks), not as code review or a passing unit test alone. Step 12 re-runs the original PoCs against the actual burn-in binary.

5. THE OVERLAY'S DELETE ARM. `overlay.get(k).unwrap_or_else(|| base.get(k))` silently resurrects any resource deleted in an earlier stage — one line, silently exploitable, and structurally identical to B2's unbonding-entry exploit. Mitigation: `Some(None) => Ok(None)` is an explicit arm with a dedicated test (test_overlay_staged_delete_is_a_hit_not_a_miss), and the overlay must cover modules as well as resources, with flush_loader_cache_if_invalidated() called after any stage that published — the Loader cache lives on MoveVM, not Session, and is the one piece of state layering does not isolate.

6. A METERED EPILOGUE WOULD REINTRODUCE FREE ABORTS. Stage 3 is empty today only because gas is a flat up-front burn. If a refund model is ever wired onto the shared, near-exhausted meter, an abort consuming the full gas_limit makes the fee write itself run out of gas and vanish — the exact spam vector the whole design protects against. Mitigation: the stage-3 seam exists from day one with a comment stating it must be unmetered plus asserted, mirroring Aptos running its abort hook with &mut UnmeteredGasMeter and then verifying the charge landed.

7. OPERATIONAL, NOT TECHNICAL. n=3 gives f=0, and there is no auto-start — one reboot froze the chain for 10 days. Neither is visible in any test suite. Mitigation: Step 10 is a gate, and the burn-in criteria include unannounced reboots of every machine.

8. EVENTS ARE A LATENT ORACLE-POISONING VECTOR. finish() returns (ChangeSet, Vec<Event>) and AINCORE discards events today. When they are wired to the API/indexer, an aborted stage's events must die with its writes — Sui's drop_writes explicitly clears events for this reason. Mitigation: capture events per stage from the start so it cannot be forgotten later.

9. RESIDUAL, OUT OF SCOPE, TICKET IT: governance.move:114-118 lets a new vote overwrite escrow.proposal_id on a merged escrow, so an old proposal's locked stake becomes claimable on the new proposal's execution. Not a B1 instance and not on the mainnet-blocker path, but it is a real fund-flow bug.
